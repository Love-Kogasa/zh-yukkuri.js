# 引擎说明:这份纯 JS 合成引擎是怎么来的

这份文档回答一个问题:`src/engine/` 里那两万多行代码,凭什么能替代原来的
v86 模拟器 + AquesTalk DLL,而且声音一模一样?

如果你不想读细节,记住三句话就够了:

1. 它是对原版 AquesTalk 引擎的**逐字节等价重写**——同样的输入,
   产生的 WAV 文件与原版 DLL 完全一致(不是"听起来像",是每个字节都一样)。
2. 一致性在开发环境里经过两万余组对比用例验证(覆盖 8 个声音与各类
   输入形态),并在 Windows 真机上加载原版 32 位 DLL 做过交叉复核。
   这套大规模验证依赖原版 DLL 与模拟器等素材,不随本仓库分发;
   数字仅作为开发侧的质量说明。
3. 仓库内自带一小组固定样本(`tests/engine.test.ts`),任何人都可以
   独立运行:改了引擎代码,跑一遍 `npm test` 就知道有没有改坏。
4. 想做“与原版对照”的复核,仓库还自带 `npm run verify`:用 v86 模拟器
   加载原版 DLL,与引擎对同一批输入各自合成、逐字节比对。需要自取的
   原版素材(v86.wasm 与 8 个 voice zip),清单见 README 的 Build 一节。

---

## 它是怎么做出来的

整个过程可以概括为"抄作业,但连标点符号都核对"。

**第一步:让原版程序当老师。** 把原版 DLL 放进一个 x86 模拟器里运行,
喂给它各种输入,把它产出的音频完整记录下来。这些记录(下称"标准答案")
就是唯一的参照物——我们从不猜"它大概是怎么算的",只看"它实际输出了什么"。

**第二步:用纯 JS 重写,对答案。** 按照观察到的行为,把合成过程拆成
五步流水线重写(文本解析 → 假名归一化 → 分词与音高 → 音素展开 →
波形渲染),每写一步就和标准答案逐字节比对,不一致就修,直到一致。

**第三步:穷举式验证。** 8 个声音 × 各种输入形态(普通假名、重音标记、
标点、促音、长音、控制字符、不同语速、真实中文语料转出的片假名……)
共两万余组,全部逐字节一致才收工。之后又在 Windows 真机上直接加载
原版 DLL 全量重跑了一遍交叉确认——排除"模拟器本身有偏差导致假一致"
的可能。验证素材(标准答案、对照组、模拟器)留在开发环境,
未随本仓库分发。

顺带一提:验证过程中发现原版程序自己就有一些"未定义行为"(比如某些
输入下会读到没初始化的内存,同样的输入有时报错、有时出声、甚至崩溃)。
这些行为不属于任何一方能保证的契约,引擎按"全新启动"的确定行为复刻,
这也是与真机冷启动状态完全一致的选择。

## 代码结构速览

```
src/engine/
├── index.ts            入口:切分短语、驱动五步流水线、暴露 synth()/run()
├── voice.ts            8 个声音的常量与假名→音素名映射
├── core/
│   ├── types.ts        全引擎共享的类型与定点运算(严格复刻整数语义)
│   └── synth-arena.ts  共享缓冲区:原版"跨短语残留"机制的内存模型
├── pipeline/           五步流水线(每步一个文件,注释里讲清了语义)
└── render/             波形渲染:激励源 + 滤波器,两个渲染族
    └── data/           8 个声音的参数表(从原版数据提取)
```

每个文件的头部注释都用中文把"这一步在做什么、为什么这么做"讲了一遍,
想深入了解的话,按 `index.ts` → `pipeline/` → `render/` 的顺序读即可。
